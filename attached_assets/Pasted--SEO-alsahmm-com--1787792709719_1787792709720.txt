# مهمة إصلاح وتدقيق SEO شاملة لموقع alsahmm.com

أريد منك تنفيذ معالجة شاملة ومدروسة لجميع ملاحظات تدقيق SEO الأخيرة، مع اعتبار أن **استقرار النظام الحالي وعدم كسر أي وظيفة موجودة أهم من إجراء أي تحسين شكلي**.

لا أريد إعادة بناء النظام، ولا إعادة كتابة أجزاء تعمل بالفعل، ولا تغييرات واسعة غير ضرورية. المطلوب هو إصلاح المشاكل المثبتة، والتحقق من المشاكل المحتملة، وتحسين ما يستحق التحسين فقط، مع إجراء اختبارات قبل وبعد كل مجموعة تغييرات.

---

## أولاً: قاعدة العمل الأساسية — ممنوع التعديل العشوائي

قبل تنفيذ أي تعديل:

* افهم آلية بناء الموقع الحالية.
* افهم مصدر توليد `sitemap.xml`.
* افهم آلية الـ prerender الحالية.
* افهم طريقة توليد `metadata`, `canonical`, `robots`, `JSON-LD`.
* افهم Routing والصفحات الديناميكية.
* افهم مصدر بيانات الخدمات والمقالات والباقات والأحياء.
* افهم قواعد البيانات المستخدمة في الإنتاج والبناء.
* حدد ما هو مصدر الحقيقة لكل نوع من البيانات.

**لا تقم بإعادة بناء أي نظام موجود لمجرد تحسينه.**

إذا كان الحل يتطلب تعديل ملف واحد، عدّل ملفًا واحدًا.

إذا كان الحل يتطلب تغيير دالة محددة، لا تعيد كتابة النظام بالكامل.

إذا وجدت مشكلة في أداة فحص داخلية، لا تعدّل الموقع لإرضاء أداة الفحص؛ أصلح أداة الفحص نفسها إذا كانت المشكلة فيها.

---

# P0 — إصلاح Sitemap بشكل نهائي

هذه هي الأولوية القصوى.

المشكلة المؤكدة حاليًا:

`https://alsahmm.com/sitemap.xml`

تُرجع `200 OK` وXML صحيح من ناحية Content-Type، لكن قيم `<loc>` المنشورة مكسورة، مثل:

`http:`

`http:/about`

`http:/pricing`

بدلاً من:

`https://alsahmm.com/`

`https://alsahmm.com/about`

`https://alsahmm.com/pricing`

## المطلوب

1. تحديد المصدر الحقيقي للمشكلة:

   * مولد Sitemap.
   * Environment Variable.
   * Base URL.
   * Reverse Proxy.
   * Build Script.
   * Deployment Script.
   * Server Rewrite.
   * أو أي طبقة أخرى.

2. عدم الاكتفاء بتعديل الملف الناتج يدويًا.

3. إصلاح المصدر الذي يولد Sitemap بحيث لا تتكرر المشكلة في النشر القادم.

4. استخدام Canonical Base URL موحد للموقع:

`https://alsahmm.com`

5. التأكد من أن جميع `<loc>`:

   * تبدأ بـ `https://alsahmm.com`
   * ليست نسبية.
   * لا تحتوي `http:`
   * لا تحتوي `http:/`
   * لا تحتوي `localhost`
   * لا تحتوي نطاقات التطوير.
   * لا تحتوي نطاقات Replit أو Preview.
   * لا تحتوي مسارات مكسورة.
   * لا تحتوي روابط مكررة.

6. التأكد من عدم وجود:

   * صفحات `noindex` داخل Sitemap.
   * صفحات غير Canonical.
   * صفحات Redirect فقط.
   * صفحات 404/410.
   * صفحات Admin.
   * API routes.
   * صفحات خاصة بالمستخدمين.

7. التأكد من أن Sitemap تحتوي فقط على URLs قابلة للفهرسة وذات قيمة.

8. لا تقم بإضافة كل ملفات HTML الموجودة في build إلى Sitemap بشكل أعمى.

# P0 — إنشاء Validation تلقائي للـ Sitemap

أريد إضافة فحص آلي يمنع نشر Sitemap تالفة مستقبلًا.

الفحص يجب أن يتحقق على الأقل من:

* XML صالح.
* عدد URLs.
* عدم وجود duplicate URLs.
* جميع URLs absolute.
* HTTPS فقط.
* Hostname صحيح.
* عدم وجود localhost.
* عدم وجود domains خاصة بالتطوير.
* عدم وجود `http:/`.
* عدم وجود `http:`.
* عدم وجود URLs فارغة.
* عدم وجود `noindex`.
* عدم وجود canonical مختلف بشكل غير مقصود.
* عدم وجود Status غير 200.
* عدم وجود Redirect غير ضروري.
* توافق URL مع سياسة الـ trailing slash الحالية.

ويجب أن يفشل الـ build/deployment أو يعطي Failure واضح إذا كانت Sitemap غير صالحة.

**المهم:** لا تجعل الفحص هشًا بحيث يمنع النشر بسبب حالة غير جوهرية. استخدم مستويات واضحة:

* ERROR = يمنع النجاح.
* WARNING = لا يمنع النشر.
* INFO = معلومة فقط.

---

# P0 — بعد الإصلاح

بعد نشر الإصلاح:

افحص Live Production وليس ملفات المشروع فقط.

تحقق من:

`https://alsahmm.com/sitemap.xml`

ثم تحقق من عينة حقيقية من URLs الموجودة في Sitemap.

لا تعتبر:

`200 OK`

دليلًا كافيًا.

يجب فحص:

`HTTP Status → HTML → Canonical → Indexability`

لكل عينة.

# P1 — Canonical وURL Architecture

راجع جميع أنواع الصفحات وليس فقط الصفحات العشرة الرئيسية.

أريد التأكد من وجود سياسة URL واحدة وواضحة.

راجع:

* Homepage
* Services
* Service Details
* Packages
* Areas
* Area Details
* Blog
* Blog Articles
* FAQ
* About
* Contact
* Privacy
* Terms
* أي صفحات ديناميكية أخرى.

يجب ألا توجد حالات يكون فيها:

Sitemap URL ≠ Canonical URL

بشكل غير مقصود.

كما يجب التأكد من أن:

`/about`

و

`/about/`

لا ينتجان صفحتين مستقلتين قابلتين للفهرسة.

إذا كانت السياسة الحالية هي النسخة بدون trailing slash، حافظ عليها في جميع الأنواع.

**لا تغيّر بنية الروابط الحالية إلا إذا ثبت وجود مشكلة حقيقية.**

لا تقم بتغيير URLs القديمة لمجرد تفضيل شخصي.

---

# P1 — Robots.txt

راجع `robots.txt` النهائي من Production.

تأكد من:

* السماح للزحف إلى المحتوى العام.
* منع Admin.
* منع API.
* عدم منع CSS/JS/images المطلوبة للرندر.
* عدم وجود Disallow واسع بالخطأ.
* Sitemap URL صحيح.
* HTTPS.
* عدم وجود قواعد متعارضة.

ثم اختبره على مجموعة من URLs المهمة.

---

# P1 — Metadata

راجع Metadata لجميع Templates وليس صفحات عشوائية فقط.

يجب التأكد من:

* Title واحد.
* Meta Description واحدة.
* Canonical واحد.
* H1 واحد.
* Open Graph.
* Twitter Card.
* `og:url` صحيح.
* `og:image` صحيح.
* عدم استخدام Title ثابت لكل الصفحات.
* عدم استخدام Description مكرر على الصفحات المحلية.

لا أريد حشو كلمات مفتاحية داخل Titles أو Descriptions.

الأولوية هي:

**نية البحث + الموقع + الخدمة + الوضوح + CTR**

وليس مجرد زيادة عدد الكلمات.

---

# P1 — Open Graph

وجد التقرير أن `/blog` يستخدم:

`/images/service-facades.jpg`

في `og:image`.

راجع جميع الصفحات.

إذا كان النظام يستخدم روابط نسبية، وحّدها إلى Absolute URLs عند الحاجة:

`https://alsahmm.com/...`

لكن لا تغير آلية الصور نفسها أو تنقل الملفات دون سبب.

تأكد من:

* الصورة موجودة.
* Status = 200.
* Content-Type صحيح.
* لا يوجد Redirect غير ضروري.
* الصورة مناسبة للمشاركة.
* OG URL مطابق للصفحة.

---

# P1 — Internal Linking

هذه نقطة مهمة للنمو العضوي.

راجع جميع صفحات الأحياء.

كل صفحة حي تجارية يجب أن تكون مرتبطة منطقيًا بـ:

* الخدمات المناسبة.
* الخدمات الأكثر طلبًا.
* المناطق القريبة عند وجود علاقة حقيقية.
* صفحات التواصل/الحجز.

لكن **ممنوع عمل شبكة روابط آلية ضخمة أو Spam**.

مثلاً صفحة حي الملقا يمكن أن تحتوي على روابط حقيقية لخدمات مثل:

* تنظيف الفلل.
* تنظيف المجالس.
* التنظيف بعد البناء.

إذا كانت هذه الخدمات مناسبة فعلًا.

لا تضف روابط لمجرد زيادة عدد الروابط.

---

# P1 — صفحات الأحياء Local SEO

هذه من أهم النقاط.

أريد مراجعة جميع صفحات الأحياء وليس الملقا فقط.

لا أريد 50 صفحة تختلف فقط باسم الحي.

كل صفحة Area يجب أن تحتوي على معلومات حقيقية ومفيدة تخص المنطقة عندما تتوفر البيانات.

مثل:

* نطاق الخدمة.
* طبيعة العقارات.
* الخدمات المناسبة.
* حالات الاستخدام.
* المناطق القريبة.
* الأسئلة الشائعة المناسبة.
* طريقة طلب الخدمة.
* CTA واضح.

**ممنوع توليد نصوص وهمية أو معلومات جغرافية غير مؤكدة.**

إذا لم تتوفر معلومة حقيقية عن حي معين، لا تخترعها.

الأفضل محتوى أقل ولكنه حقيقي ومفيد من صفحات كثيرة بمحتوى متشابه.

---

# P1 — منع Thin / Duplicate Local Pages

أريد تنفيذ فحص تشابه داخلي للصفحات المحلية.

حدد الصفحات التي تحتوي على نسبة عالية جدًا من المحتوى المتكرر.

لكن:

**لا تقم بحذف أو دمج أي صفحة تلقائيًا.**

أخرج تقريرًا أولًا يوضح:

* URL.
* Similarity.
* المحتوى المتكرر.
* المحتوى الفريد.
* القرار المقترح.

ثم يمكن اتخاذ قرار منفصل.

لا تستخدم `noindex` كحل سريع لمشكلة محتوى ضعيف إلا بعد التأكد أن الصفحة لا تستهدف Intent تجاريًا مهمًا.

---

# P1 — CTA

أضف CTA واضحًا حيث توجد نية تجارية.

خصوصًا:

* About.
* Blog.
* Service pages.
* Area pages.
* Packages.

أمثلة:

"اطلب خدمة التنظيف"

"احجز الآن"

"تواصل معنا عبر واتساب"

يجب أن يكون CTA منطقيًا ومتناسقًا مع تصميم الموقع.

لا تحول المقالات إلى صفحات إعلانية.

---

# P1 — Service Pages

راجع صفحات الخدمات.

يجب أن تكون كل خدمة قادرة على الإجابة عن:

* ما الخدمة؟
* لمن تناسب؟
* ماذا تشمل؟
* كيف يتم تنفيذها؟
* ما الذي يميزها؟
* ما المناطق التي تغطيها؟
* الأسئلة الشائعة.
* كيفية طلب الخدمة.

إذا كانت هناك خدمة مهمة وتفتقد خطوات تنفيذ واضحة، أضف محتوى حقيقيًا مناسبًا للخدمة.

لا تستخدم Template واحدًا مع استبدال اسم الخدمة فقط.

---

# P1 — Structured Data

راجع كل JSON-LD الموجود.

لا أريد إضافة Schema لمجرد زيادة العدد.

أريد:

* Schema صحيحة.
* Schema متوافقة مع محتوى الصفحة.
* عدم وجود بيانات غير حقيقية.
* عدم وجود Reviews أو Ratings وهمية.
* عدم تضخيم OfferCatalog.
* عدم تكرار نفس Entity بطرق متعارضة.

راجع خصوصًا:

* LocalBusiness / النوع الأنسب فعليًا.
* WebSite.
* BreadcrumbList.
* Article.
* FAQPage.
* Service.
* Offer / OfferCatalog.

وتأكد أن كل Schema تمثل المحتوى الموجود فعليًا في الصفحة.

---

# P1 — Reviews / Ratings

هذه نقطة حساسة.

إذا كانت بيانات التقييم الموجودة في Schema لا تستند إلى تقييمات حقيقية يمكن إثباتها، فلا تحاول الحفاظ عليها فقط لأنها تبدو جيدة للـ SEO.

راجع مصدر:

* ratingValue
* reviewCount
* reviews

وتأكد من مطابقتها للمصدر الحقيقي.

إذا لم تكن قابلة للإثبات، يجب عدم اختلاقها أو إبقائها بطريقة قد تعتبر Misleading.

---

# P1 — Local Business / NAP

راجع بيانات النشاط التجاري.

يجب توحيد:

* الاسم.
* الهاتف.
* الموقع.
* المدينة.
* المنطقة.
* بيانات التواصل.

بين:

* الموقع.
* Structured Data.
* Google Business Profile.

لا تضف Address أو Geo Coordinates غير مؤكدة.

# P1 — Breadcrumbs

تأكد من وجود BreadcrumbList في الصفحات التي تحتاجها.

لكن لا تضف Breadcrumbs للصفحات التي لا يكون لها معنى.

ويجب أن:

* تطابق المسار الحقيقي.
* تحتوي على URLs صحيحة.
* لا تحتوي على صفحات وهمية.
* لا تحتوي على localhost.
* لا تستخدم أسماء غير متوافقة مع الصفحة.

---

# P2 — Blog SEO

راجع نظام المقالات بالكامل.

التأكد من:

* Title فريد.
* Description مناسبة.
* Canonical.
* Article Schema.
* datePublished.
* dateModified.
* Author عندما يكون متاحًا وحقيقيًا.
* Featured Image.
* Alt.
* Internal Links.
* Related Services.
* Related Areas عند وجود علاقة حقيقية.

`dateModified` يجب أن يعكس تعديلًا حقيقيًا، وليس تغيير التاريخ تلقائيًا مع كل Build.

---

# P2 — الصور

راجع جميع الصور المهمة.

تأكد من:

* Alt مناسب.
* وجود الصورة.
* عدم وجود Broken Images.
* WebP/AVIF حيث يكون مناسبًا.
* عدم تحميل صور ضخمة بلا داعٍ.
* Lazy Loading للصور غير الحرجة.
* أبعاد width/height عند الإمكان لتقليل CLS.
* الصور المهمة Above the Fold لا تتأخر بلا داعٍ.

لا تقم بتحويل أو ضغط جميع الصور عشوائيًا إذا كان النظام الحالي يستخدم Pipeline جيدة.

# P2 — Performance

لا تفترض أن الموقع سريع فقط لأنه يستخدم Prerender.

نفذ اختبار فعلي على Production.

على الأقل:

1. Homepage.
2. Service page.
3. Area page.
4. Article page.

اختبر:

* LCP.
* INP.
* CLS.
* TTFB.
* Total Blocking Time عند استخدام Lighthouse.
* حجم HTML.
* حجم JS.
* حجم الصور.
* عدد Requests.

استهدف:

* LCP < 2.5s
* INP < 200ms
* CLS < 0.1

لكن لا تقم بتحسين الأداء بطريقة تكسر:

* SEO.
* JavaScript.
* الصور.
* Tracking.
* Navigation.
* Booking.
* Forms.

---

# P2 — Security / Headers

راجع HTTP Headers في Production.

التقرير أشار إلى غياب HSTS.

تحقق أولًا من إعدادات Hostinger/Proxy/Server.

إذا كان HTTPS مستقرًا على جميع النطاقات والـ subdomains المطلوبة، يمكن إضافة:

`Strict-Transport-Security`

بإعداد آمن ومدروس.

لكن لا تضف:

`includeSubDomains`

أو `preload`

بشكل أعمى قبل التأكد من أن جميع النطاقات الفرعية تعمل HTTPS بشكل صحيح.

أي Header جديد يجب اختباره قبل اعتماده.

---

# P2 — Broken Links / Link Integrity

نفذ Crawl فعلي للموقع.

أريد تقريرًا عن:

* 404.
* 410.
* 301.
* 302.
* Redirect Chains.
* Broken Internal Links.
* Broken Images.
* Broken Canonicals.
* Broken hreflang إن وجد.
* Broken Sitemap URLs.

لا تقم بتغيير الروابط القديمة عشوائيًا.

إذا وجد Redirect مطلوب، استخدم 301 بشكل صحيح.

---

# P2 — قاعدة البيانات وأدوات الفحص

التقرير ذكر أن:

`check-links.mjs`

يتوقف بسبب قاعدة بيانات ثانوية لا تحتوي جدول:

`posts`

تعامل مع هذا كخطأ في أداة التدقيق وليس كدليل على وجود مشكلة في الموقع.

المطلوب:

1. تحديد لماذا الأداة تحاول استخدام قاعدة البيانات الثانوية.
2. تحديد مصدر البيانات الصحيح.
3. جعل الفحص يتعامل مع عدم وجود قاعدة البيانات الثانوية بشكل آمن.
4. عدم إنشاء جدول Fake فقط لإسكات الخطأ.
5. عدم تعديل Production Database بلا حاجة.
6. يجب أن تفرق الأداة بين:

   * Tooling Error.
   * Data Error.
   * Website Error.

ثم أعد تشغيل الاختبارات.

---

# P2 — Build / Prerender

التقرير أثبت أن البناء ينتج صفحات كثيرة.

أريد التأكد من أن الـ prerender لا ينتج:

* صفحات مكررة.
* URLs غير قابلة للوصول.
* HTML قديم.
* Metadata قديمة.
* Sitemap مختلفة عن الصفحات الفعلية.
* صفحات تعتمد على بيانات غير موجودة.

عدد الصفحات الناتجة ليس هدفًا بحد ذاته.

**الجودة والفهرسة الصحيحة أهم من زيادة عدد الملفات.**

---

# P2 — Sitemap Coverage

بعد إصلاح Sitemap، قم بمقارنة:

Database URLs

مع

Prerender URLs

مع

Sitemap URLs

مع

Internal URLs

مع

Canonical URLs.

أريد معرفة الفروقات.

يجب ألا تدخل صفحة مهمة في Sitemap ولا تكون قابلة للوصول من الموقع.

وفي المقابل، الصفحات المهمة تجاريًا يجب ألا تكون孤立ة بدون Internal Links.

# منع المشاكل التالية صراحةً

أثناء التنفيذ:

* لا تحذف المقالات.
* لا تحذف الخدمات.
* لا تحذف صفحات الأحياء.
* لا تغير URLs الحالية دون سبب مثبت.
* لا تغير تصميم الموقع بالكامل.
* لا تغير نظام Routing بالكامل.
* لا تغير قاعدة البيانات بدون ضرورة.
* لا تضف Keywords بشكل مصطنع.
* لا تضف نصوصًا مكررة.
* لا تولد Reviews وهمية.
* لا تضف معلومات جغرافية غير مؤكدة.
* لا تضف Schema غير مدعومة بالمحتوى.
* لا تستخدم noindex لإخفاء مشاكل الجودة بشكل عشوائي.
* لا تضف آلاف الروابط الداخلية آليًا.
* لا تضف آلاف الصفحات بهدف زيادة حجم الموقع.
* لا تغير Titles الحالية الجيدة بدون سبب SEO واضح.
* لا تغير Canonicals العاملة بدون سبب.
* لا تستبدل نظام Prerender الحالي بنظام آخر.
* لا تغير Framework أو Stack.
* لا تعمل Refactor واسع unrelated بالـ SEO.
* لا تعتبر نجاح Build دليلًا على نجاح SEO.
* لا تعتبر Status 200 دليلًا على صلاحية الصفحة.
* لا تعتبر وجود Schema دليلًا على أهليتها للظهور في Rich Results.

# نظام التحقق المطلوب قبل اعتبار المهمة مكتملة

بعد التعديلات نفذ دورة كاملة:

## 1. Build

يجب أن ينجح Build بدون أخطاء.

## 2. SEO Gate

يجب أن ينجح:

* Titles.
* Descriptions.
* Canonicals.
* H1.
* Robots.
* Sitemap.
* Internal Links.
* JSON-LD.
* Noindex conflicts.

## 3. Production Crawl

افحص الموقع الحقيقي وليس Build فقط.

## 4. Sitemap Validation

يجب أن تكون كل `<loc>` صحيحة.

## 5. HTTP Validation

افحص عينة كبيرة من Sitemap URLs.

## 6. Canonical Validation

تأكد من تطابق:

Sitemap URL

مع

Canonical URL

عندما يكون ذلك مقصودًا.

## 7. Indexability Validation

تأكد من عدم وجود:

`noindex`

أو Robots blocking على الصفحات المهمة.

## 8. Structured Data Validation

اختبر الأنواع المهمة بعد التعديل.

## 9. Performance

نفذ Lighthouse/PageSpeed على الصفحات الأربع الرئيسية المذكورة.

## 10. Regression Test

تأكد أن:

* الموقع يفتح.
* Navigation يعمل.
* الخدمات تعمل.
* المقالات تعمل.
* صفحات الأحياء تعمل.
* النماذج تعمل.
* WhatsApp/CTA تعمل.
* الصور تعمل.
* Mobile layout لم يتأثر.
* Desktop layout لم يتأثر.

# المطلوب في التقرير النهائي

لا تكتفِ بقول "تم الإصلاح".

أريد تقريرًا واضحًا يحتوي على:

### 1. المشاكل التي تم اكتشافها

مع:

* Severity.
* السبب.
* الملف/المكان المسؤول.
* التأثير.

### 2. التعديلات التي تمت

لكل تعديل:

* الملف.
* ما الذي تغير.
* لماذا.
* لماذا هذا التغيير آمن.

### 3. المشاكل التي لم يتم تعديلها

مع سبب عدم تعديلها.

### 4. نتائج الاختبارات قبل وبعد

مثل:

* Sitemap.
* Crawl.
* Broken Links.
* Canonicals.
* Metadata.
* Schema.
* Build.
* Performance.

### 5. المشاكل المتبقية

أي مشكلة لم يتم حلها يجب ذكرها بوضوح.

### 6. توصيات مستقبلية

افصل بين:

* ضروري.
* مهم.
* اختياري.

# معيار النجاح

لا أريد الوصول إلى "10/10" عن طريق رفع أرقام شكلية أو إجراء تغييرات كثيرة.

الهدف الحقيقي هو:

**موقع مستقر + قابل للزحف + قابل للفهرسة + Sitemap سليمة + Canonical صحيحة + محتوى محلي حقيقي + Internal Linking منطقي + Structured Data صحيحة + Performance جيدة + عدم وجود Regression.**

أي تعديل لا يخدم واحدًا من هذه الأهداف بشكل واضح لا تقم به.

**اعمل بمنهج محافظ ومحسوب على مستوى النظام بالكامل، واعتبر الموقع الحالي هو Production System يجب الحفاظ عليه، وليس مشروعًا نريد إعادة بنائه من الصفر.**

ابدأ أولًا بالتحليل الكامل ومقارنة الحالة الحالية، ثم نفذ P0، وبعد نجاح اختبارات P0 انتقل إلى P1، ثم P2.

لا تنفذ جميع التغييرات دفعة واحدة دون Validation بين المراحل.
